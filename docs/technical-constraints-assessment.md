# apache_web 技术限制条件全景评估

> 文档状态：项目暂时定稿阶段评估
>
> 评估范围：架构、交付、3D 渲染、视觉、动画、性能、交互、资产、测试、协作、归档，以及 Phase 0–12 期间形成的阶段性约束。

## 1. 总体结论

apache_web 已形成一套“源码约束—构建检查—浏览器回归—性能采样—归档复核”的完整交付链路。其核心路线是：单文件 HTML、零运行时依赖、外置 3D 资产、程序化视觉、固定随机、统一状态源和严格验收。

这套路线以扩展自由度换取交付确定性。对于当前的 AH-64E 交互式 3D 展示页，这种取舍总体成功：项目获得了较好的离线能力、可复现性、状态一致性、性能可控性和发布可信度。但如果未来继续向高质量 3D 产品、复杂游戏系统或长期多人协作开发演进，主模型缺少源资产、源码层面的模块解耦不足、全局状态过度集中，将成为主要瓶颈。

总体建议不是解除所有限制，而是分成三类处理：

- 长期保留的系统不变量：单次色彩转换、固定随机、唯一状态源、对象池、构建门禁、条件等待和资产验收。
- 改造成配置或预算的软约束：粒子量、辉光层数、阴影尺寸、DPR、对象池容量、武器参数、地形参数和导览时长。
- 当前阶段或资产条件造成的临时约束：禁止源码 ESM、数字前缀依赖、直接使用 Blender 原始节点名、缺少 `.blend/.fbx`、只能用独立 GLB 补件以及人工归档流程。

## 2. 限制分类总览

| 类别 | 主要限制 | 总体判断 |
|---|---|---|
| 交付 | 单文件 HTML、零 npm、零 CDN、外置 GLB | 发布优势明显，扩展能力受限 |
| 架构 | 数字前缀排序、共享 IIFE、禁止 import/export | 当前规模有效，规模扩大后会成为负担 |
| 模型 | 原始节点名、实测包围盒、UV 依赖 | 能保证当前资产稳定，但阻碍换模和高模升级 |
| 源资产 | 缺少 `.blend/.fbx` | 当前最严重的长期瓶颈 |
| 渲染 | Linear、NoToneMapping、末端唯一 sRGB、手写后处理 | 正确性和风格控制强，调参门槛较高 |
| 视觉 | 实时程序化生成、固定随机、可感知验收 | 可复现且有特色，但真实感上限受预算限制 |
| 状态动画 | `FLY` 唯一状态源、根节点逐帧重建、真实状态窗口 | 一致性强，复杂演出自由度降低 |
| 性能 | 对象池、质量档位、自动降档、三角形和 draw call 预算 | 稳定性强，限制高端画质和复杂玩法 |
| 交互 | 键鼠、Pointer Events、失焦清理、移动端共用状态 | 可靠性高，输入系统复杂 |
| 测试 | 有头 Chromium、本地 GPU 权威、`__dbg`、peak-hold | WebGL 测试可信，但 CI 覆盖不完整 |
| 协作 | 改前重读、多 AI 交接、阶段停工复核 | 降低覆盖风险，但流程成本较高 |
| 归档 | Git 差异唯一真源、LF 补丁、干净 worktree 验证 | 可复核性强，发布流程较重 |

## 3. 交付与运行环境限制

### 3.1 单文件 HTML

Three.js、GLTFLoader 和全部应用代码必须构建到 `dist/index.html`。这使最终部署简单、版本边界清晰、离线归档方便，也便于对最终产物做哈希比较。

劣势是 HTML 会持续变大，浏览器首次解析和编译压力增加，开发者工具定位困难，代码分割和按场景懒加载不自然。单个模块的小改动也会改变整个产物，难以做局部发布。它不直接降低 GPU 帧率，但会增加启动 CPU 成本，并可能放大贴图合成、模型初始化和测试时序竞态。

建议保留“发布产物是单文件”，但解除“源码必须以单文件思维开发”的限制。开发阶段可以使用多文件模块、源码映射和独立测试，构建阶段仍输出单文件。

### 3.2 零 npm、无框架、无打包器、无外部 CDN

优势是没有网络供应链、版本漂移、第三方服务故障和运行时依赖，适合离线演示和长期保存。

劣势是模块管理、状态管理、后处理、组件复用、动画系统、兼容性和调试工具都需要自行维护。复杂视觉和游戏功能的开发速度低于成熟引擎或标准前端工程，外部开发者上手也更依赖项目内部文档。

建议继续保持零运行时依赖和零 CDN；允许开发环境使用工具链，最终产物仍保持零依赖。

### 3.3 GLB 和贴图外置，必须走 HTTP

外置 GLB 避免 Base64 膨胀，保留浏览器的二进制加载与缓存能力，也便于单独替换资产。代价是最终交付需要 HTML、GLB、贴图和正确的静态服务器，不能直接双击 HTML 运行。路径、MIME 类型、服务器配置或资产缺失都可能导致启动失败。

建议增加资产清单、版本号、文件大小和哈希校验，并在页面中提供可理解的资产加载错误提示。

## 4. 模块架构限制

### 4.1 数字前缀排序拼接

`src/app/*.js` 按数字前缀排序后拼接，文件顺序承担依赖顺序。优势是实现简单、构建确定、无需打包器；劣势是依赖关系隐藏在文件名和全局引用中，插入新模块需要人工重新安排顺序，循环依赖和初始化时序问题不够直观。

它会提高新功能的升级成本：新增天气、编队、任务或动画系统时，不仅要写功能，还要决定插入编号、初始化先后和入口依赖。

建议保留数字前缀作为构建兼容机制，但逐步增加模块命名空间、`init/update/dispose` 生命周期和注册表，使数字不再是唯一的架构边界。

### 4.2 禁止 `import/export`，共享 IIFE 顶层作用域

优势是与单文件交付一致，构建简单；缺点是全局变量冲突、隐式依赖、难以单测、难以估计重构影响范围。`WeaponRig`、`70-app.js` 和多个视觉系统实际共享较多状态，模块表面分离但内部仍然耦合。

建议在源码中建立显式 `Runtime` 或命名空间对象，区分公共 API、只读状态和可写状态。未来可以源码使用 ESM，发布时再编译为 IIFE。

### 4.3 模块契约和拓扑检查

`docs/module-contracts.md` 强制登记 `depends` 和 `provides`，构建时检查反向引用、依赖白名单和符号提供关系。

这是非常有价值的限制，能防止架构无序膨胀，也适合多 AI 协作。负面影响是任何跨模块小改动都需要同时修改契约、代码和测试，降低快速视觉试验的速度。

建议继续保留，但区分核心公共 API、实验性视觉模块和配置数据，避免所有细小参数都产生同等级别的契约负担。

## 5. 模型与资产限制

### 5.1 依赖 Blender 原始节点名

如 `Cylinder.010`、`BODY.001` 等节点名同时被配置、模型绑定、测试和离线工具使用。优势是当前模型绑定精确、实现简单；劣势是 Blender 导出命名成为程序接口。只要对象重命名、合并网格、改变层级或重新导出，旋翼、武器挂点、灯光、爆炸视图、涂装分区和机位都可能失效。

这会直接限制换模型、换导出器和引入更高精度资产。

建议增加资产适配层，把原始节点名映射为稳定的语义 ID，例如 `body`、`rotor`、`gun`、`sensor`、`weapon_mount`，产品代码不再直接引用 Blender 原始名字。

### 5.2 包围盒、挂点和飞行常量必须实测

`exact_bounds.py`、`dump_tree.py` 等工具用于从当前 GLB 测量结构、坐标和包围盒。优势是避免凭感觉填写坐标，能够防止机体漂浮、埋地、武器错位和机位穿模。

劣势是任何资产改动都可能要求程序重新测量和修改常量，资产制作与程序开发高度耦合。包围盒只能表达粗略空间关系，不能证明曲面接触、法线方向、遮挡或真实贴合。

建议继续保留 bbox 实测，同时增加接触面距离、法线方向、最小间隙、射线投射和多机位验收。

### 5.3 没有 `.blend/.fbx` 源资产

这是当前最大的长期瓶颈。没有源文件就无法修改主模型拓扑、UV、法线、材质分区、骨骼和动画，也无法把新增细节真正并入主资产。

因此 P10 只能走独立低模 GLB 路线，容易产生比例不一致、穿模、悬空、阴影不连续、材质不统一和额外 draw call。远景可能合格，近景机首、轮组、传感器和武器挂点的真实感上限则被主模型硬性限制。

建议把 `.blend`、导出设置、贴图源文件、材质说明、语义节点映射和资产版本哈希纳入正式归档。源资产应被视为生产基础设施，而不是可有可无的开发便利。

### 5.4 部分部件没有有效 UV

缺少 `TEXCOORD_0`、单点 UV 或退化条带会限制接缝、磨损、铆钉、污渍、贴花和镜片细节。程序化材质可以快速提升有有效 UV 部件的质量，但无法可靠修复无 UV 部件。

具体后果是部分 P9 细节只能变成材质数值微调，肉眼不明显，或被迫延期到 P10 几何阶段；贴花也可能拉伸、镜像或在局部重复。

建议优先补齐源资产 UV。无法改模时可使用 triplanar mapping、世界空间噪声、顶点色、程序化法线或独立 decal mesh，但这些只能作为适配方案。

## 6. 渲染与视觉限制

### 6.1 单次色彩转换

Renderer 使用 Linear 输出和 `NoToneMapping`，后处理末端统一进行一次 sRGB 编码。

优势是避免重复 gamma、辉光能量错误、亮部提取异常和材质颜色失真，也让后处理管线具有明确的线性工作空间。

劣势是调参门槛较高。开发者不能按屏幕 RGB 直觉直接修改颜色；ACES 可能将灯芯压成白色，高光会掩盖低对比度材质细节，新增后处理也必须理解整个色彩链路。

该限制应长期保留，但应提供线性/显示色调调试、后处理阶段截图和统一颜色工具函数。

### 6.2 手写后处理

亮部提取、高斯 mip 链、辉光、ACES、色散、暗角和颗粒全部由项目自行控制。优势是风格独特、无外部依赖、可以按场景裁剪。

劣势是每增加一种效果都可能增加 framebuffer、纹理带宽、shader 编译和移动端兼容成本。水面、雾、粒子、灯效和后处理同时启用时，必须在画质与帧率之间取舍。

### 6.3 实时程序化视觉，不能依赖预渲染帧

优势是机体、地形、灯光、粒子、武器、下洗和水面能够随相机与输入变化，交互真实性高，也不需要存储大量视频资源。

劣势是实时 GPU 预算限制了全局光照、高采样反射、复杂体积云、电影级运动模糊、高质量透明和多层阴影。复杂动画、爆炸、编队和救援演出都必须在每帧预算内完成。

### 6.4 固定种子随机

所有视觉随机使用 `mulberry32/rnd()`，禁止 `Math.random()`。优势是草地、贴图、粒子和程序化细节每次刷新一致，便于截图回归和问题复现。

代价是场景长期变化不足，草屑、沙尘和纹理细节每次都在相同位置。未来应区分视觉种子、会话种子、任务种子和测试种子，而不是简单解除固定随机。

### 6.5 地形高度场同源

`duneH` 等地形数据同时服务于沙丘、沙脊、下洗贴花、目标位置和相关效果。优势是物理、目标和视觉位置一致；劣势是改一个地形参数可能牵动目标布阵、任务路线、救援点和效果位置。

同源数学也不保证观感正确。下洗环曾出现物理概念正确但视觉上像雷达靶标的问题，说明还需要独立的视觉包络、断续噪声和顺风偏置。

## 7. 性能与资源限制

### 7.1 对象池和不可随意销毁资源

武器、粒子、草屑、水花、碎片和介质效果使用对象池。瞬态结束时通常只隐藏对象、清除飞行数组，不销毁 geometry/material。

优势是减少 GC、资源重建、shader 编译和 GPU 抖动。劣势是池容量必须预估，池内共享材质限制单对象差异，长期运行时常驻资源会增加内存压力，场景卸载也更困难。

建议按生命周期分级：高频对象常驻池，场景专属对象切换时释放，大型纹理和后处理目标按需要重建，并记录池命中率、峰值和占用。

### 7.2 `applyQuality()` 唯一画质入口

画质入口统一控制 pixel ratio、后处理级别、粒子、草、水花、细节件和相关效果。优势是不会出现只改 UI 文案而不降低真实 GPU 负载的假降档。

劣势是质量系统集中，新增效果必须同时设计档位策略。固定档位也不能完全适配不同设备：有的设备受 fill rate 限制，有的受 draw call、shader 或 CPU 更新限制。

建议保留唯一入口，但内部改为预算驱动，分别管理 DPR、后处理、粒子、阴影、纹理和 CPU 更新预算。

### 7.3 三角形、draw call 和阴影预算

性能记录和阴影策略使系统能稳定运行在约 60 fps，但也限制了草地、沙尘、反射、动态灯光、敌人数量、粒子和高精度阴影的规模。新增玩法必须与视觉效果争夺同一帧预算。

小件默认不投射阴影可以节省 shadow pass draw call，但近景部件会缺少接触阴影和立体融合。建议对近景关键件使用局部阴影、烘焙 AO、接触阴影或法线近似，而不是全局开启阴影。

## 8. 飞行、状态与动画限制

### 8.1 `FLY` 是唯一状态源

起飞、悬停、降落、俯冲、FPV 平移和移动端摇杆都必须通过 `FLY`。优势是键盘、鼠标、触屏、导览和 HUD 不会各自维护平行飞行状态。

劣势是 `FLY` 逐渐成为高耦合中心。新增自动驾驶、损伤偏航、编队飞行、AI 僚机或多实体系统时，现有扁平状态结构可能不足。

建议保持“单一事实来源”，但将状态分域为 Flight、Camera、Weapon、Mission、Input 和 Visual State，并由协调器提交变更。

### 8.2 根节点每帧重建，外部位移必须走 `FLY.x/z`

这能避免位置漂移、重复累加和重置失效，但也意味着开发者不能直接修改 `root.position`。新机位、碰撞推离、任务位移和过场平移都必须理解状态合成机制；绕过通道的改动会在下一帧被覆盖。

### 8.3 导览必须遵守真实状态窗口

导览启动、旋翼转速、起飞和控制权交接必须基于真实状态，而不能单纯按固定秒数跳转。优势是演示状态与实际交互一致；劣势是电影式时间轴自由度降低，必须使用“高度达到阈值、旋翼达到阈值、状态稳定”等条件触发。

## 9. 交互和无障碍限制

### 9.1 统一输入路由

键盘、按钮、chip、Pointer Events、指针锁定、触屏和全局快捷键必须有明确让位规则。伪按钮需要 `role=button`、`tabindex=0`、键盘行为和 `aria-pressed`；机位条使用 radiogroup/radio/`aria-checked`。

优势是键鼠、触屏和辅助技术行为一致。劣势是事件路径复杂，新增控件必须同时考虑默认 DOM 行为、全局快捷键、PointerEvent、重复按键和焦点状态，容易出现空格双触发或按钮误触发武器等问题。

### 9.2 失焦、后台和指针取消必须释放状态

`blur`、`visibilitychange`、`pointercancel` 和指针锁定丢失都必须释放扳机、按键、摇杆和拖拽状态。优势是避免页面切后台后武器持续发射、摇杆卡住或恢复时残留输入；劣势是正常路径之外的测试和清理分支明显增加。

### 9.3 移动端复用桌面状态通道

优势是没有第二套驾驶状态机，桌面端与移动端逻辑不易分叉。劣势是陀螺仪、触觉、复杂手势和移动端专属辅助功能需要先映射到键盘/`FLY` 模型，表达能力不如原生移动交互模型。

### 9.4 HUD 不能整体 `aria-hidden`

因为 HUD 中仍包含指针锁定恢复入口和触屏方向键。该限制保护了可操作性，但使视觉隐藏、屏幕阅读器语义和交互可用性必须分别维护，增加 UI 状态复杂度。

## 10. 音频限制

音效通过 Web Audio 实时合成，不能依赖采样文件；AudioContext 必须在用户手势后启动。

优势是零音频资产依赖、文件体积小，并可根据转速、距离、武器和飞行状态动态变化。劣势是程序化音效的真实机械纹理、空间感和长时间听感通常不如高质量录音；浏览器自动播放策略和移动端音频兼容也增加了测试成本。

建议保留程序化音效作为基础方案，同时允许未来部署可选的本地高质量采样包。

## 11. 测试和验收限制

### 11.1 有头 Chromium和本地 GPU

headless/SwiftShader 会导致游戏时间与墙钟时间严重失真，因此 Playwright 必须使用有头 Chromium，Windows 窗口还不能被原生窗口遮挡。

优势是起降、粒子、灯效、武器和帧率测试更接近真实用户环境；劣势是完整 WebGL 门禁不能完全依赖普通 CI，浏览器、驱动、GPU 和窗口状态都成为测试前提。

### 11.2 CI 只承担静态和帧率无关门禁

Linux CI 无真实 GPU，适合执行构建、语法、DOM、拓扑和结构断言，不适合实时 WebGL 视觉和帧率验收。

优势是假失败更少；劣势是提交合并时无法完全证明画面、粒子、灯效、起降动画和实际帧率没有回归。建议保留本地 GPU 权威，同时增加固定 GPU runner 的夜间任务，以及运行时状态轨迹、shader 编译、资产哈希和对象池计数等无像素替代指标。

### 11.3 `__dbg` 数值出口与条件等待

动态测试应读取 `window.__dbg` 状态，并用 `wait_for_function` 等待异步值收敛；状态设置和事件派发应在单次 `evaluate` 内原子完成。

优势是比读取中文 DOM 文本和固定墙钟更可靠，能减少测试竞态。劣势是测试与内部状态接口耦合，产品必须长期维护调试出口。建议将其规范化为只读诊断 API，区分状态快照、性能指标和 peak-hold 事件。

### 11.4 窄脉冲和像素判定

100–250 ms 的灯效、炮口焰和闪烁必须使用 peak-hold；像素测试用主色占优，而不是简单 RGB 通道上限。

这些限制提高了测试可信度，但只能证明效果发生或主色出现，不能完全证明位置、形状、比例和艺术质量。因此仍需要运行时数值、离线几何、多机位截图和真人验收结合。

## 12. 协作和归档限制

### 12.1 多 AI 修改前重读文件

优势是降低并行覆盖、基于旧内容修改和阶段交接错误。劣势是增加上下文读取成本，且多个 AI 同时改核心文件仍然容易产生冲突。

建议配合文件所有权、修改窗口、变更摘要、自动冲突检查和阶段性集成提交。

### 12.2 Git 差异是归档唯一真源

`changed_files` 必须来自 `git diff --name-only <baseline>..HEAD`；记忆同步后必须重新计算；`DIFF.patch` 需要以 LF 写出并在干净基线 worktree 上执行 `git apply --check`。

优势是归档可复核、可迁移，不易漏记 `CODELY.md` 或产生不可应用补丁。劣势是发布流程较重，Windows 子进程、CRLF、Git 锁文件和 worktree 都可能增加操作风险。

建议将提交、记忆同步后的重算、补丁生成、干净 worktree 验证和最终报告串成一个发布命令。

## 13. 阶段性限制及其影响

### 13.1 P9 材质精修边界

P9 原则上不改几何，只做材质级细节。它清晰地区分了材质问题和几何问题，控制了阶段预算；但铆钉、接缝、边缘和传感器等真正需要几何的细节只能延期。

### 13.2 P10 独立几何件路线

没有主模型源文件时，P10 只能生成独立低模 GLB。它让项目可以继续补充局部几何，但牺牲了结构融合、比例、接触、阴影和材质统一性。机首件穿地和尺寸失控说明早期仅检查中心点是不够的，必须检查世界 bbox、离地、尺寸、方向、接触和间隙。

独立 GLB 只能作为当前资产条件下的补救路线，不能成为长期高质量建模管线。

### 13.3 P11 教学、挑战和跨端

训练和任务变体必须复用正式控制通道和状态机。优势是用户学到的操作与正式玩法一致；劣势是教学不能使用一套更容易编排的假逻辑，设计自由度较低。

### 13.4 P12 发布审计和真人验收

七维审计、门禁、性能、归档和真人验收能够防止“自动测试通过但肉眼不合格”。代价是发布速度较慢，人工验收还受到设备、分辨率、屏幕亮度和机位差异影响。

真人验收应继续保留，但需要记录设备、DPR、浏览器、场景、机位和判定标准。

## 14. 对六个核心维度的综合影响

### 14.1 3D 渲染

正面作用是色彩链路、资产实测、资源池化和质量档位让渲染稳定可控。负面作用是主 GLB、UV、节点名和缺少源文件压低了几何、材质、法线、AO、接触和高模烘焙的上限。

### 14.2 视觉呈现

正面作用是程序化涂装、固定种子和统一后处理带来可复现且有辨识度的风格。负面作用是程序化公式可能“数学正确但观感错误”，低对比度细节可能不可见，粒子、辉光和阴影也会因预算被削弱。

### 14.3 动画设计

正面作用是统一状态源和真实状态窗口保证动画与交互一致。负面作用是复杂演出必须服从状态机、实时帧预算和条件触发，电影式时间轴、编队、多实体和损伤动画的自由度较低。

### 14.4 性能调优

正面作用是对象池、质量档位、自动降档、阴影限制和性能历史使 60 fps 目标可管理。负面作用是同一预算限制粒子、反射、后处理、敌人数量、动态灯光和复杂互动；常驻池还可能增加长期内存压力。

### 14.5 游戏互动

正面作用是键鼠、触屏、A11y、模式切换和异常清理得到统一治理。负面作用是输入路径复杂，新功能必须处理焦点、重复按键、PointerEvent、失焦、后台、指针锁定和触摸取消。

### 14.6 模块升级

正面作用是模块契约、拓扑检查、唯一入口和唯一状态源防止架构失控。负面作用是数字前缀、共享 IIFE、全局符号和 `70-app.js` 的集中编排使大型功能升级越来越昂贵。

## 15. 应保留、软化和解除的限制

### 15.1 必须长期保留

应保留单次色彩转换、固定随机机制、唯一事实状态源、统一画质入口、对象池生命周期管理、DOM 与拓扑构建门禁、条件等待、peak-hold、世界 bbox 与接触验收、资产哈希和 Git 差异归档。

### 15.2 应改造成配置或预算

粒子数量、草屑密度、水花数量、辉光层数、阴影尺寸、DPR、武器散布、任务时间、导览时长、地形包络、对象池容量、目标数量和纹理分辨率都应由质量档位、设备能力和游戏模式共同决定，而不应散落为硬编码常量。

### 15.3 应逐步解除

应逐步解除源码禁止 ESM、所有模块共享 IIFE 顶层作用域、数字前缀直接承担依赖、产品代码直接依赖原始节点名、没有主模型源文件、只能使用独立 GLB 补件、所有音效只能实时合成，以及完全依赖人工维护归档流程等限制。

## 16. 后续升级优先级

### 第一优先：补齐主模型源资产和语义资产管线

保存 `.blend`、贴图源、UV、材质、导出设置、节点语义映射和版本哈希。它是解除 P10 几何瓶颈、提高近景真实感和支持骨骼动画的前提。

### 第二优先：将全局状态改造成分域状态

保留唯一事实来源，但分离 Flight、Camera、Weapon、Mission、Input 和 Visual State，减少 `70-app.js` 与 `FLY` 的中心化压力。

### 第三优先：从固定质量档位升级为预算系统

继续通过 `applyQuality()` 统一入口，但内部采用分项预算，让不同设备分别调整 DPR、后处理、粒子、阴影、纹理和 CPU 更新量。

### 第四优先：建立资产适配层

将 Blender 原始节点名、运行时 saneName、挂点和包围盒转换为稳定语义接口，避免未来换模型时修改大量产品代码。

### 第五优先：自动化发布归档

将测试、提交、记忆同步后的 changed_files 重算、LF 补丁、干净 worktree 验证、构建哈希和最终报告整合成单一命令。

## 17. 最终判断

当前限制条件整体上是合理的，并且已经帮助项目达到“稳定、可复现、可测试、可交付”的定稿状态。它们的主要代价集中在自由度：高模和近景细节受资产限制，复杂动画受状态机限制，复杂视觉受实时性能限制，模块升级受全局 IIFE 和集中入口限制。

因此，后续不应为了追求扩展性而解除色彩、状态、测试和资源管理等基础约束；真正应该解除的是资产不可编辑、源码层面的伪模块化和过度集中的状态结构。

最终方向应是：

> 保留质量与可复现性约束，解除资产和源码层面的结构性限制；将性能参数从硬编码规则升级为可观测、可配置、可按设备适配的预算系统。
